# 年表の書き方

[English](timeline-format.md) | 日本語

年表(`data/events/`)の行の書き方。Pull Requestで年表の行を足す・直す人は、この文書だけ読めば済むようにしている。仕組みの設計は[design.ja.md](design.ja.md)、要件は[要件定義](../REQUIREMENTS.ja.md)にある。①〜⑤は、要件定義の5つの工程(①条件・②世界・③年表・④実装・⑤梱包)を指す。括弧の日付は、その決まりを決めた日。

年表は1件を1行のJSONで持ち、項目は6つのまとまりに分ける(2026-10-30決定)。

## 置き場所

- `data/events/<年表>/<年>.jsonl` に置く。年表は国ごと(`jp` のような2文字)と、世界共通の出来事(.NETやWindowsの版など)を入れる `world` の2種類。
- EUのような地域の年表は作らない。地域で決まった出来事は、各国の年表に書き足す(EUの指令は国ごとに国内法になる日が違うので、そのほうが正確でもある)。
- 会社が読むのは、自分の国の年表と世界年表。第1版で作るのは `jp` と `world` の2つ。
- titleとimpactは、年表ごとにその土地の言葉で書く(`jp` は日本語)。`world` は英語。
- 年は「知られた日」の年。作業日で絞るとき、未来のファイルを開かずに済む。PRの点検で、ファイルの年と知られた日の年が同じかを確かめる。

## 項目

| まとまり | 項目 | 要否 | 中身 |
| --- | --- | --- | --- |
| 見分ける | id | 必須 | 国-年-短い名前(例:jp-2012-ctax8-law)。連番にしない |
| 見分ける | thread | 段階が2行以上の話だけ | 同じ話の段階をつなぐ名前(例:jp-ctax8) |
| いつ | known | 必須 | 知られた日。YYYY・YYYY-MM・YYYY-MM-DDのどれか |
| いつ | occurred | cancelled以外は必須 | 起きた日。effective以外の段階では、その時点の予定日。まだ決まっていなければ空(cancelledも空) |
| 何が | kind | 必須 | 種類(law・standard・tech・society) |
| 何が | stage | 必須 | 段階(decided・confirmed・changed・effective・cancelled) |
| 何が | title | 必須 | 見出し |
| 何が | impact | 必須 | 業務システムにどう響いたか(1行)。1行で書けない出来事は集めない |
| どこに響く | industries | 必須 | 業種。ISIC Rev.4の大分類のアルファベット、全業種は `*` |
| どこに響く | areas | 必須 | 業務。ラボの10語から1つ以上 |
| 確かさ | sources | 必須 | 出典のURL(1つ以上) |
| 確かさ | status | 必須 | unverified(未確認)・verified(確認済み) |
| 確かさ | verified | 確認済みのとき必須 | 確かめた日(on)と誰か(by) |
| 時代の点検 | tech | kindがtechのとき必須 | 道具(product)と版(version)、見分け方(markers) |

国は置き場所で決まるので、項目には持たない。

occurredの「空」は、JSONの `null` で持ち、キーは消さない(例:`"occurred":null`)(2026-11-11決定)。

## 1行の見本

```json
{"id":"jp-2012-ctax8-law","thread":"jp-ctax8","known":"2012-08","occurred":"2014-04-01","kind":"law","stage":"decided","title":"消費税率8%への引き上げが法律で決まる(実施は2013年秋に最終判断)","impact":"税率を固定値で持つ販売・会計・請求の仕組みは、施行日で税率を切り替える改修が要る","industries":["*"],"areas":["sales","accounting","billing"],"sources":["https://..."],"status":"unverified"}
```

## 知られた日

知られた日は「担当者が対応を始められる根拠が公になった日」とする。

| 種類 | 知られた日 | 起きた日 |
| --- | --- | --- |
| law | 法律は成立した日。政令・省令・告示は公布された日 | 施行された日 |
| standard | 発表された日 | 適用された日 |
| tech | 発売・提供が始まった日 | 同じ日(サポート終了なら終了の日) |
| society | 起きた日 | 同じ日 |

- 年月まで・年までしか分からないときは、索引ではその期間の末日に知られたものとして扱う。未来が混ざらない側に倒すため。
- 検討段階の報道や噂は入れない。噂は会社の出来事の側で扱う([設計](design.ja.md)の2章)。
- サポート終了は、終了の予定日が公になった日をknownにしたdecidedの行と、終了の日のeffectiveの行で持つ。Microsoftの製品のように、発売のときに終了の予定日が決まっているものは、発売の日をknownにする。延長されたらchangedの行を足す。
- 製品名や終了日が書いていない方針の発表で終了日が決まったものは、その方針が公になった日をknownにする。担当者が終了日を計算できる根拠が公になった日だから。出典は、方針の発表とその製品のライフサイクルのページの2つ(2026-10-31決定。例:2004-05-25の延長サポートを5年に広げる方針で、2003年の製品の終了日が決まった)。
- 1行は1つの出来事。titleに書いた出来事とknownの日は同じ出来事を指し、出典にその日が書いてあること(2026-10-31決定)。製品ごとに正しい発売日を1つに決めない。同じ製品・同じ版でも、別の出来事(企業向けの提供、一般向けの発売、別のOSで使えるようになる、など)は別の行にする。
- titleには、出典に書いてある出来事の言い方(ローンチされる、RTMになる、一般提供が始まる、など)を使う。「ships」のような、どの出来事か分からない言い方は使わない(2026-10-31決定)。
- 出典がMicrosoftの公式ライフサイクルのページだけの行は、titleを「発売される」とし、日はそのページの「開始日」にする(2026-10-30決定。10-31に、上の決まりの中での日の取り方に位置づけを変えた)。1つの公式ページで確かめられるため。
- 同じ製品・同じ版で、今ある「発売される」の行より早い提供(企業向けの提供、ボリュームライセンス向けの提供、一般提供など)が出典で確かめられたら、別のeffectiveの行として足す。会社は、条件を満たす提供のうち一番早い日から使えるため([設計](design.ja.md)の2章)。今ある行と同じ日の提供は足さない(2026-11-11決定)。
- 製品の利用開始(発売・提供が始まる)を表すeffectiveの行は、その日に始まったことを、当日以降に出た出典で確かめてから足す。事前の予告(「〇日に提供を始める予定」など)だけでは足さない。事後の出典が見つかったら足す(2026-11-11決定)。
- 同じ版の出来事が2行以上あるときは、markersはどれか1行だけに付ける。点検で同じものを2回拾わないため。

## 段階とthread

段階を踏む話は段階ごとに1行にし、同じthreadでつなぐ。

| stage | 意味 | 日付の決まり |
| --- | --- | --- |
| decided | 決まった | 起きた日は知られた日より後。日付がまだ決まっていなければ空(未定) |
| confirmed | 実施や日付が、法律・政令などで確定した | 起きた日は知られた日より後 |
| changed | 変わった(延期・前倒し・中身の変更) | 起きた日は知られた日より後。日付がまだ決まっていなければ空(未定) |
| effective | 実施された・起きた | 知られた日と起きた日が同じ |
| cancelled | 取りやめになった | 起きた日は空 |

- 作業日の時点の予定は、同じthreadのうち、知られた日が作業日以前で一番新しい行の起きた日。その行がcancelledなら、有効な予定はない。cancelled以外で起きた日が空なら、予定日は未定と読む。threadのない1行だけの出来事は、その行を読む(2026-11-11、[設計](design.ja.md)の2章を決めたときに補足)。
- 段階の行は追記だけで、前の行は書き換えない。間違いを直すための書き換えはかまわない。
- 実質決まった日と、日付が正式に確定した日がずれる話は、行を分ける。実質決まった時点(法律の成立、首相の正式な表明など)をdecidedかchangedの行にし、日付が法律や政令で確定した時点をconfirmedの行にする。知られた日は、それぞれの時点の日(2026-11-11決定)。
- 震災や製品の発売のように1行で終わる出来事は、effectiveの1行だけで、threadは付けない。

例:消費税10%(日付は仮。下書き集めで出典を確かめる)

| 段階 | 知られた日 | 起きた日 | ファイル |
| --- | --- | --- | --- |
| decided(法律で決まる) | 2012-08 | 2015-10-01 | jp/2012 |
| changed(1回目の延期) | 2014-11 | 2017-04-01 | jp/2014 |
| confirmed(1回目の延期の法律が成立) | 2015-03 | 2017-04-01 | jp/2015 |
| changed(2回目の延期) | 2016-06 | 2019-10-01 | jp/2016 |
| confirmed(2回目の延期の法律が成立) | 2016-11 | 2019-10-01 | jp/2016 |
| effective(実施された) | 2019-10-01 | 2019-10-01 | jp/2019 |

## 種類・業種・業務

| kind | 中身 | 例 |
| --- | --- | --- |
| law | 法令・制度(税、改元、公的な料金制度も含む) | 消費税、改元、マイナンバー |
| standard | 業界の規格・取り決め | 全銀協の形式、文字コードの規格 |
| tech | 製品・技術 | .NETの版、Windowsのサポート終了 |
| society | 社会・経済・災害 | 震災、リーマンショック |

- 業種はISIC(国際標準産業分類)Rev.4の大分類のアルファベット(A〜U)。細かく分けたくなったら下の桁を足す(例:C10)。Rev.5はJから後ろの記号の意味が変わるので混ぜない。Rev.5に移るときは、国連の対応表でまとめて一度に付け替える(2026-11-11決定)。
- 業務は次の10語:accounting(会計)・sales(販売)・billing(請求)・purchasing(購買)・inventory(在庫)・production(生産)・logistics(物流)・payroll(給与)・hr(人事・勤怠)・platform(基盤:OS・DB・文字コードなど)。

## 確かさ

- 出典は1件に1つ以上。末尾の追跡用の目印(utm_sourceなど)は外す。消えたページはWeb Archive(web.archive.org)のURLでよい。
- 確認済みにするときは verified に日付と誰かを残す。例:`"verified":{"on":"2026-11-02","by":"claude-code-cloud"}`
- 確認済みが外れるのは「事実の欄」(known・occurred・stage・sources・techのproductとversion)が変わったときだけ。title・impact・industries・areasは言葉や判断の欄で、直しても外れない。こちらは③で人が年表を読むときに見る。techの2つは、[設計](design.ja.md)の2章で「その版をいつから使えたか」の鍵にしたので加えた(2026-11-11決定)。
- 確かめ役が、開いた出典のとおりに直した行は、その場で確認済みにしてよい。新しい出典が要る直しや、行を分ける・足す直しは未確認に戻す。
- 確かめるのは使う分から。1本作るときに、①の条件(国・年代・業種)にかかる未確認の行をスクリプトが一覧にし、確かめ役にまとめて渡す。
- 「別の会話が確かめたか」は機械では確かめきれないので、手順書で守る。

## 時代の点検の見分け方

kindがtechの行に `tech` を付ける。

```json
"tech":{"product":"csharp","version":"5.0","markers":[{"lang":"cs","name":"async/await","pattern":"\\basync\\s+(Task|void)\\b"}]}
```

- 点検のスクリプトは、会社がその時点で使う道具の版より新しいtechの出来事を集め、そのmarkersをコードに当てる。基準は日付ではなく会社の道具の版。
- 機械は疑わしい箇所を拾うまで。判定は点検役がする(正規表現はコメントや文字列の中にも当たるため)。
- VB.NETとC#で同じ時期に入った機能は、1つの出来事にlang違いのmarkersを並べる。langは cs・vb のほか、ソリューションファイル(sln)とプロジェクトファイル(proj)も使える。コードに現れない出来事(サポート終了など)にはmarkersを付けない。
- productは第1版では csharp・vbnet・dotnet-framework・visualstudio・windows・sqlserver・office・crystalreports の8つに絞り、ほかはPRで足す(visualstudio・office・crystalreportsは2026-10-30に追加)。
