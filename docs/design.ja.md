# 仕組みの設計

[English](design.md) | 日本語

legacy-labの基本設計のうち、仕組みの設計。年表の書き方は[timeline-format.ja.md](timeline-format.ja.md)、要件は[要件定義](../REQUIREMENTS.ja.md)にある。章の番号は、基本設計を決めたときの議題の番号のまま(1章は年表の書き方)。①〜⑤は、要件定義の5つの工程(①条件・②世界・③年表・④実装・⑤梱包)を指す。括弧の日付は、その決まりを決めた日。

## 2. ③で会社の出来事をどう作るか

会社の業務・人物・制約と、確認済みの世の中の出来事をつないで、会社の年表を作る。③で全体の骨組みを人が確かめ、④では前の実装に合わせて、その時期の資料の細かいところを足す(2026-11-11決定)。

### 5つの方針

| 決めること | 決まったこと |
| --- | --- |
| 出来事の起点 | 会社の業務・人物・制約と世の中の出来事をつなぎ、誰が何に困り、なぜ改修するかを説明する。世の中の出来事が関わらない、社内だけの出来事も作れる |
| 細部を作る時期 | ③で出来事・日付・Phase・作業日・業務の目的・対象の範囲・利用環境を固める。④で前の実装を見て、その時期の細部を足す |
| Phaseの区切り | 業務として引き渡せる改修の単位で区切る。目的・変える範囲・触らない範囲・前のPhaseとの関係を示す |
| 回答者が知っていること | 人物ごとに、担当の範囲・作業日までに知っていること・必要なときに渡せる資料を用意する。範囲の外は「分からない」と答える |
| その時期の資料の量 | 依頼メモ、必要最小限の実物(CSVなど)、その時期の人物と環境を用意する。CSVとテキストを基本にする |

### ②から④までの流れ

1. ② 世界を作る。①の言語・年代・業種・国・規模から、架空の会社・人物・部署・業務・もとからあるシステムと資料・担当者の経験・会社が使う道具の版を作る。人物ごとに、知っている範囲と分からないことを置く。
2. ③ 材料を選ぶ。国・業種・年代に合う確認済みの世の中の出来事を候補にし、②で決まった業務に合わせてareasで絞る(①の条件にareasは足さない)。使う年表の版と行のidを控える。
3. ③ 会社の出来事を作る。「きっかけ → 困る人 → 会社の対応 → 業務の変更 → 今回触らない範囲」で点検する。取引量が増える、拠点が増える、担当が替わる、例外の条件、監査、二重入力などを会社の設定に結びつける。悪いコードという結末に合わせて、出来事をこしらえない。
4. ③ Phaseに分けて人に見せる。SQLiteから1〜2ページの年表を出す。時期・世の中の出来事・会社の出来事・改修の目的・Phase・利用環境を並べ、知られた日と起きた日の違いも読めるようにする。人物と資料の詳しいところは別添にし、直しを入れてから④へ進む。
5. ④ その時期の資料を具体にする。前の実装に実際にある挙動・サンプル・指摘する箇所と、その時点の知識での説明だけを足す。違いがなければ「違いなし」とする。ない不具合や、未来をにおわせる材料は作らない。

③の骨組みを変えないと直せない矛盾は、原因と差分を残して③の直しに戻す。人の停止地点はふだん①・③・⑤で、Phaseごとの承認待ちは増やさない。HTMLは見るためのもので、OKと直しの依頼は、利用者のエージェントとの会話で受ける。

### 会社の出来事の持ち方

- 時間と確認の決まりは[年表の書き方](timeline-format.ja.md)のとおり。会社の出来事にも同じ骨組み(known・occurred・stage・thread)を使う。置き場は世の中の出来事と分け、日付とthreadで抜き出す処理(索引のスクリプト)は共通にする。
- 会社だけの情報(人物・業務・世の中の行への参照・Phaseなど)は、足しの情報として持つ。
- 架空の設定がかみ合っているかの点検と、世の中の事実の「確認済み」は分ける。会社の出来事に、こしらえた出典URLを付けない。
- 噂は「会社に噂が伝わった」という会社の出来事として置く。噂の中身を確認済みの事実として扱わず、stageに噂のための値は足さない。確報や対応の変更は、別の行として追記する。
- 起きるのが作業日より後でも、作業日までに知られていれば見せてよい。知っていることと、実際に使えることは分ける(使えるかは次の節)。

### 会社の道具の版と、いつから使えたか

- 会社の道具は、世の中の年表のtech.productと同じ呼び名(csharp・vbnetなど)と版で持つ。採用した出来事と、利用開始の根拠にした行のidを控える。
- 根拠にするのは、同じproduct・versionで発売・一般提供などの利用開始を表す、確認済みで作業日の時点で知られたeffectiveの行。会社が提供範囲・契約などの条件を満たす候補のうち、一番早いoccurredを採る。発表・終了予定・サポート終了の行は候補にしない。
- 候補は、threadごとに作業日の時点の最新の状態を確かめてから選ぶ。あとの変更や取りやめを、過去へさかのぼらせない。
- 道具を実際に使えるのは「利用開始日 ≦ 作業日」かつ「会社での採用が始まる日 ≦ 作業日」のとき。発売されただけでは、会社の環境は変わらない。
- 利用開始の行は、②でidをはっきり控える。titleの文字を探すだけで、自動で決めない。
- 根拠が足りない、提供の条件が分からない、同じ日に矛盾がある、日付が粗くて開始日を決められない、のどれかなら、使えると推定しない。そこは「要確認」にして、②では人を待たずに③へ持ち越し、③で人に見せる年表にまとめて出す。人の停止地点は①・③・⑤のまま増やさない。④で出たものは、今までどおり③の直しに戻す。
- 月まで・年までのoccurredは、実際の日を補わずにそのまま持つ。その期間の途中から使えるとはしない。

### その時期のものだけを渡す

- 作業日はラボが決める。日付で絞ったあと、人物の担当と知っている範囲で、さらに絞る。参照先や、必要なときに渡す資料も同じ境目を通す。
- 元のDB・年表の全体・未来の資料・脚本家の内部メモは、担当者と回答者の作業フォルダへ渡さない。配るファイルの一覧・日付・参照先・脚本の混じりを点検してから、担当者を動かす。
- 担当者は、判断・理由・迷った案・影響の範囲を判断メモに残す。⑤では点検の報告とビルドの結果を人へ示し、コード・年表・判断メモをひと組にする。

### 1本目で測ること

1〜2日という目標に届くか、Phaseの数・資料の量・質問の回数・AIの使用量の上限は、まだ測っていない。1本目で測る。

## 3. 点検役が見てよい範囲

点検役は、作業日の外から見る人にする。未来まで見てよい代わりに、指摘の渡し方で作業日の境目を守る。点検は各Phaseの終わりに、そのPhaseの差分で行う(2026-11-11決定)。

### 3つの方針

| 決めること | 決まったこと |
| --- | --- |
| 見てよい範囲 | 世の中の年表の全部、脚本(②世界と③年表)の全部、全Phaseのコードと判断メモ、機械の点検の結果 |
| 報告の行き先 | 人向けの報告と、担当者向けの直しの依頼の2通に分ける |
| 動く時期 | Phaseごと。各Phaseの終わりに、そのPhaseの差分だけを見る |

### 見てよい範囲

- 作業日の境目は、コードを書く人に未来を混ぜないためのもの。点検役はコードを書かず読むだけなので、境目の内側に閉じこめない。
- 点検役のいちばんの仕事は、過去のコードに混ざった未来を見つけること。担当者のAIは学習で未来を知っているので、うっかり混ぜることがある(例:2015年のPhaseのコードに、令和に備えた和暦の処理がある)。
- 指摘には、根拠にした年表の行のid(作業日より後に知られた出来事)か、会社の道具の版を書く。
- 点検役はコードを直さない。担当者・回答者とは話さない。
- 点検役の会話を、担当者・回答者に使い回さない。未来を見た会話が、作業日の内側に入らないため。会話の分け方は使う人に任せるので、手順書で守る。

### 報告の行き先

- 人向けの報告には全部書いてよい。どのPhaseの、どのファイルの何行目が、どの年表の行や会社の道具の版に合わないか、直したか残したかまで書く。
- 担当者向けの直しの依頼は、作業日の内側の言葉だけで書く。未来の出来事の名前や日付は書かない(例:「作業日の資料にない元号は入れず、資料にあることだけで作る」)。
- 直しの依頼は、2章の「配るファイルの一覧・日付・参照先・脚本の混じり」の点検を通してから担当者へ渡す。新しい関所は作らない。
- 骨組みを変えないと直せないものは、2章のとおり③の直しに戻す。

### 動く時期

1. Phaseが終わったら、機械の点検(markers)を当てる。
2. 点検役が、機械が拾った箇所を判定し、そのPhaseの差分で雰囲気と未来の混ざりを見る。
3. 直すものがあれば、直しの依頼を担当者へ渡し、そのPhaseの中で直す。
4. 点検役が、直したところだけもう一度見る。

- 直しの往復は1回まで。もう一度見ても残ったものは、残したまま⑤の報告に書く。点検が止まらなくなって、AIの量がふくらむのを防ぐため。
- ⑤では、Phaseごとの報告をスクリプトがまとめて人に見せる。人の停止地点は①・③・⑤のまま増やさない。
- 最後に通しで全体を見る点検が要るか、点検役のAIの量がどれくらいかは、1本目で測る。重すぎたら、⑤でまとめて見る形などに変える。

## 4. リポジトリの構成

配る仕組みと年表はlegacy-labのリポジトリに置き、1本ごとの作業場はリポジトリの外、完成物は1本ごとに別のリポジトリにする。基本設計はこの章のあと、リポジトリのdocs/へ移して正本にする(2026-11-12決定)。

### 6つの方針

| 決めること | 決まったこと |
| --- | --- |
| 置き場の分け方 | リポジトリには配る仕組みと年表だけを置く。1本ごとの作業場はリポジトリの外。完成物は1本ごとに別のリポジトリ |
| リポジトリのフォルダ | 仕組みは1つのPythonパッケージ(legacylab/)にし、`python -m legacylab <やること>` で呼ぶ |
| 作業場の区画 | script・control・work・answer・review・preview・output の7つ |
| 文書の置き場所と言葉 | 基本設計はdocs/へ移して正本にする。日本語が正本で英語を並べる。指示書は英語の1組 |
| PRの自動点検 | 点検はlegacylabの命令にし、CIはそれを呼ぶだけ |
| ライセンス | ルートはMIT、data/ はCC BY 4.0。READMEとCITATION.cffに両方を書く |

### リポジトリのフォルダ

```
legacy-lab/
  README.md              エージェントが最初に読む入口
  REQUIREMENTS*.md       要件
  data/events/           年表の正本
  legacylab/             Pythonの仕組み(標準ライブラリだけ)
  instructions/          脚本家・担当者・回答者・点検役の指示書
  templates/             完成物のREADMEやビルドのひな形
  tests/                 仕組みのテスト
  docs/                  決まりの文書
  .github/workflows/     PRの自動点検と仕組みのテスト
  LICENSE・CITATION.cff  ライセンスと引用
```

- 作業日の境目の決まりは legacylab/ の1か所に置き、索引・作業フォルダへの書き出し・混ざりの点検・直しの依頼の点検・人が見るHTMLのすべてがそれを使う。同じ決まりを何度も書くと、1か所ずれただけで未来が漏れるため。
- 追加のインストールは要らない。要件の「小さなスクリプト」は、やることごとの命令を小さく保つ形で守る。

### 1本の作業場

作業場はリポジトリの外に、1本ごとに作る(例:legacy-lab-runs/<1本の名前>/)。場所は設定で仕組みに教える。担当者の手の届く範囲に、年表の全体と脚本を入れないため。のぞかない約束より、手の届かない置き場のほうが確か。

| 区画 | 中身 | 使う人 |
| --- | --- | --- |
| script | 脚本(②世界と③年表の全部)、元のSQLite | 脚本家。点検役は読むだけ |
| control | 条件・作業日・③で採った内容・計測 | 仕組み(legacylab)。作業日は担当者・回答者には変えられない |
| work | 作業日で絞った表、その時期の資料、コード、判断メモ、質問 | 担当者 |
| answer | 回答者の人物ごとの資料と答え | 回答者 |
| review | 人向けの報告と、直しの依頼の下書き | 点検役 |
| preview | 人が見る1枚のHTML | 人(①・③・⑤) |
| output | ⑤でまとめる完成物 | 梱包 |

- 区画のあいだのやり取りは、どれも境目の点検を通す。担当者の質問は回答者へ、回答者の答えはworkへ、点検役の直しの依頼もworkへ。
- それぞれのAIは、自分の区画を作業の場所として起動する。
- answerをworkと分けるのは、回答者の「必要なときに渡せる資料」を、担当者が聞かずに読めないようにするため。聞いて初めて渡る形にしないと、本物らしいやり取りにならず、1本目で測る質問の回数も測れない。

### 文書の置き場所と言葉

```
docs/
  timeline-format.ja.md / timeline-format.md   年表の書き方(1章)。PRを出す人の入口
  design.ja.md / design.md                     仕組みの設計(2〜4章)
```

- 日本語版を正本にし、英語版の頭に「日本語版が正本」と書く。年表の書き方を別のファイルにするのは、PRを出す人がそこだけ読めば済むようにするため。同じ決まりを2か所に書かない。
- 移すのは4章のあと、実装の前。決まりの直しはたいていコードの直しと一緒に起きるため、決まりもリポジトリで直す。
- 指示書(instructions/)は英語の1組。指示書はAIがそのとおりに動く文書で、2組あるとそのずれが1本の出来のずれになるため。指示書には「画面の言葉・コメント・資料・判断メモは、①で決めた国の言葉で書く」と入れる。

### PRの自動点検

点検は `python -m legacylab check` にして、CIはそれを呼ぶだけにする。手元でもPRでも同じ点検になり、PRを出す人が出す前に確かめられる。

| まとまり | 確かめること |
| --- | --- |
| ファイル | 1行1つのJSONか、ファイルの年とknownの年が同じか |
| 欄 | 必須の欄がそろっているか、kind・stageが決まった値か、areasが10語のどれかか、industriesがRev.4の記号(A〜U、下の桁つきも可)か`*`か、techが要る行にあるか、同じ版でmarkersが2行以上にないか |
| 日付 | known・occurredの形(occurredの「空」は `null` でキーを残す)、段階ごとの日付の決まり |
| id | 形と、重なりがないか |
| 確かさ | 出典が1つ以上で追跡用の目印がないか、verifiedにon・byがあるか、確認済みのまま事実の欄が変わった行がないか(PRの前と比べる) |
| commit | メンテナーのcommitの作者とコミッターがnoreplyか |

- commitの点検は、メンテナーのcommitだけを見る。ほかの人のメールは見ない。メンテナーの非公開のメールを公開の設定ファイルに書かない形で作る。GitHubのpushの柵は、いちばん新しいcommitしか見ないので、この点検で全部のcommitを見る(2026-11-11に、メンテナーのアカウントのメールを非公開にし、そのpushの柵もオンにした)。
- 仕組みのテストは、Windows・Mac・Linuxの3つで回す。完成した1本のビルドの点検(Windowsのマシン)は、templates/ のひな形に入れる。

### ライセンス

- ルートのLICENSE(MIT)はそのまま。data/ にCC BY 4.0のLICENSEを置き、READMEとCITATION.cffに両方を書く。
- PRを出す人向けに「data/ に出した行はCC BY 4.0、仕組みはMITで出したものとする」と書く([年表の書き方](timeline-format.ja.md)の最後)。
- 年表のデータは、はじめルートのMITのまま公開していた。ほかの人のPRが入る前に、docs/へ移したのと同じPRでCC BY 4.0に直した。
- 完成した1本には成り立ちとして年表の行が入るので、templates/ のREADMEのひな形に、出どころ(CC BY 4.0)の表示の欄を入れる。
